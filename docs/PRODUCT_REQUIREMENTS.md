# 产品需求：NX AI Assistant

## 1. 产品定义

一个直接运行在 Siemens NX2512 内部的 AI 助手插件。它提供聊天窗口，接受自然语言、参数和文件输入，读取当前活动零件，通过插件自身的 NXOpen 集成实时建模，并向用户反馈实际结果。

它不是后台 `.prt` 生成器，不是 MCP 客户端，不依赖外部代理或编码代理，也不是独立启动的第二个 NX 进程。

## 2. 用户体验

- NX 主界面有专用菜单项/按钮。
- 按钮打开一个 modeless 浮动聊天窗口；不要求原生停靠。
- 同一时间只保留一个主聊天窗口，重复点击时激活现有窗口。
- 窗口可移动，NX 主界面在窗口打开时仍可交互。
- NX 退出时，聊天窗口、网络任务、日志资源和插件资源有序关闭。
- 聊天体验接近通用 AI 聊天窗口：多轮对话、消息状态、错误信息、取消请求、文件附件。
- 能清晰显示当前活动零件名称、建模操作计划、执行状态、成功/失败后的真实模型变化。

## 3. 模型 API

- 在插件设置页直接配置 Base URL、模型 ID、API Key、温度/输出限制等适用参数。
- 通过插件内部 HTTP 客户端直接访问提供商，不经 MCP、外部 Agent 或本地中转服务。
- 使用可扩展 Provider 接口；首个适配器可以支持 OpenAI-compatible Chat/Responses 风格，但必须在运行时正确处理各提供商差异，不能假设所有 API 一致。
- 支持流式响应时逐步显示回答。
- 处理超时、取消、限流、无效密钥、模型不支持工具调用、服务端错误等情况。
- API Key 不写入源代码、日志、测试样例或版本控制；本地存储采用 Windows DPAPI/Credential Manager 等机制。

## 4. 文件附件

- 第一阶段先定义附件模型与大小/类型限制。
- 按实现成本优先支持纯文本、Markdown、CSV、常见文档提取文本。
- 图片输入、CAD 图纸或其他二进制内容仅在模型提供商确实支持且数据处理已实现时开放。
- 上传文件不应自动执行其中的命令或代码；外来内容只能作为待分析数据。

## 5. NX 当前模型上下文

至少逐步支持查询：

- NX 会话与工作部件/显示部件状态
- 部件路径、单位、名称
- 实体、特征树和参数表达式
- 面/边/坐标等几何上下文（按 NXOpen 可用能力逐步实现）
- 当前选中对象与相关几何
- 操作前后的模型状态和特征变化

读取当前 NX 模型是建模规划的基础。不得默认以空白部件或独立测试文件替代用户当前部件。

## 6. 实时建模

- 初期支持创建新部件和在当前工作部件上执行有限、可验证的特征操作。
- 模型输出应尽量使用 NX 原生参数化特征并保留特征树。
- 所有 NXOpen 读写必须通过已验证的 NX 内部执行线程/调度方式。
- 网络调用在后台运行，不能冻结 NX UI。
- 工具/动作是有类型的接口，模型只能选择注册的操作并提供参数；不允许不受约束地执行 LLM 生成的任意代码。
- 操作前检查前置条件；面引用、定位点、目标实体或方向不明确时向用户询问。
- 对会显著改变模型的动作给出计划/确认选项；失败时尽可能撤销或恢复。
- 执行后从 NXOpen 读取实际状态验证结果，不信任模型的文字声称。

## 7. 生命周期与安装

- 插件生命周期隶属 NX 进程；NX 关闭时妥善清理窗口、请求、事件订阅和资源。
- 提供面向兼容 NX2512 安装环境的一键安装/升级/卸载流程。
- 安装程序检测 NX 安装路径和版本，部署插件程序集、入口/菜单配置和默认目录，不覆盖用户模型或设置。
- 首次启动时引导配置 API，不要求安装 MCP、Python 服务或其他 Agent。
- 安装包发布前必须在干净的 Windows/NX 环境验证安装、加载、卸载与升级。

## 8. 版本兼容、升级与部署

- NX2512 是首个开发和验收基线，产品架构必须支持未来更高版本的 NX/Designcenter；不能把 NX2512 路径、程序集版本、运行时和 API 行为硬编码到所有层。
- 将通用聊天/Provider/对话编排/工具 schema/配置逻辑与 NXOpen 版本相关的 Host Adapter 分离。共享层不得直接依赖某个版本安装目录中的具体 NXOpen 程序集。
- 启动时探测正在运行的 NX 版本、已加载的 NXOpen 程序集路径/版本及宿主运行时，选择经过验证的兼容性配置。
- 通过能力注册/适配器契约管理建模工具。某个版本缺少或改变 API 时，只禁用或替换受影响能力，不让单个差异扩散到所有功能。
- 首版可以只正式支持 NX2512，但必须建立版本支持清单、构建配置和验证流程，为后续版本增加单独的适配器构建留出空间。
- 不保证一个 DLL 不经重建就可跨所有 NX 版本工作。不同版本需要时应分别构建、测试和打包与其程序集/运行时匹配的宿主适配器。
- 安装器应枚举同一电脑上已安装的 NX 实例，为每个明确支持的实例部署正确版本的插件组件；不覆盖其他 NX 版本的文件。
- 插件升级与 NX 版本迁移分开管理：升级保留 API 配置、加密密钥引用、聊天记录及用户设置；设置文件采用有版本号的 schema 并提供迁移和回滚。
- 更新包必须有版本号、目标 NX 版本范围/明确版本列表、目标运行时、所需 NXOpen 依赖信息、校验和及升级说明。未知版本不允许无提示安装为“已支持”。
- 每次跟进新 NX 版本时，检查官方发布说明、API 变更资料和可用的 NXOpenReporter 迁移报告；用目标版本自己的 NXOpen 参考程序集构建，并完成实际加载与独立测试部件验证。
- 兼容性状态至少区分：`planned`、`built`、`loaded`、`integration-tested`、`supported`。单元测试或编译成功不能直接把某版本标记为 supported。

## 9. 延后范围

- 装配相关能力在零件建模闭环稳定后扩展。
- 仿真功能更晚扩展；不能挤占首版实时零件建模目标。

## 10. 首版验收

1. 插件通过 NX 主界面入口启动。
2. modeless 聊天窗口打开且不会重复创建。
3. 能配置模型 API 并成功发送/接收消息。
4. 能读取当前打开零件的基本信息。
5. 能通过一个已注册的 NXOpen 工具实时修改当前活动零件。
6. 修改能反映在同一个 NX 会话的几何和特征树中。
7. 插件能检查操作结果，并对失败给出准确反馈。
8. 退出 NX 时资源能正常清理。

任何仅能在后台生成独立 `.prt` 文件的方案都不满足首版核心验收。
